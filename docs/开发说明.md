# 开发说明

## 本轮要能完成的事（10 月 31 日）

本轮计算版本为 v0.4。旧运行保留原结果和版本；重试会核对版本，不用新算法覆盖旧结果。

拿到一批新材料后，先问“哪条材料值得继续查”，再问“查清后能支持什么判断”。同一个来源可以同时出现临床试验、经营数据和公共卫生信息，程序分别检查适用的方法，共享本轮人工处理名额。

- **读材料。** 新查询策略默认最多读 32 个原件版本、累计 10 万字符。一个长文件分几段读，仍算一个版本。旧 baseline 保留原来的读取范围。
- **算数字。** datasets/narrative.py 检查主体、指标、数值、期间各自的原文位置。规则不够时，narrative_execution.py 使用统一模型调用选择字段。数字换算、利用率和可比期间变化由程序计算；缺分母、期间不明或口径不同就列出来。
- **继续追。** reading_execution.py 点读当前清单中的固定原件；fetch_execution.py 申请上游支持的公开来源补采。取得采集运行编号后，恢复时只查这个编号，不再提交一次。
- **长期看。** 专题保存证据变化、关注热度、风险判断和是否继续跟踪。尚待查清的公共卫生风险，不因几天没新消息自动关闭。
- **控制费用。** 手动调查、材料更新、普通监测和专题分别记录入口。自动任务共用日额度，专题另有自己的额度；额度不足保留任务等下一日。预算等待不再消耗执行时限，真实模型调用时间和用量照常记录。
- **交付正文。** 数据库、页面原文、Markdown 和 JSON 使用同一份最终文字。来源索引由程序另附，全文核验与所选支持片段复核分别展示。

收到回执后的恢复优先读取已保存结果。重启不会因重新算剩余额度把已经复查的修订稿退回旧稿。请求结果不清楚时保留待核状态，不自动重复付费。


## 多方向 KDD 的职责与数据流（2026-10-30 实现与验收边界）

当前隔离分支 `codex/radar-kdd-20261030` 已实现四方向的业务数据加工、纯计算和逐候选评价，并复用普通 HTTP/RQ 保存真实运行。它没有替换现役主目录，也不表示所有报告、全部来源和科学效果均已通过。实际版本、失败、回归及真实报告结论集中见 `evaluation/handoff-verification.json`；施工前的只读现状保留在[资产盘点](资产盘点.md#10-月-30-日-kdd-架构核查)。

### 分析数据和纯算法的边界

来源 → Fabric 固定原件/清洗字段 → 可并行构建的检索索引、图投影与 Radar 分析数据 → 纯算法全部候选 → 逐项价值/容量评价 → 调度补证及适用专业服务 → 版本化判断和报告。数据加工直接使用完整的已采用成员或有说明的有界窗口，不拿搜索 top-k 当总体。当前合并仍限定同一明确 `source_instance`，来源许可逐项核对。

| 层 | 当前代码与返回值 |
|---|---|
| 业务数据加工 | `research/datasets/build.py:build_dataset`，复用 `mining/prepare.py`；返回稳定单位、成员、原件/映射/特征版本、时点、范围分母、排除、未知和截断 |
| 纯算法 | `research/mining/kdd.py:run_kdd`；只读固定数据和参数，不查上游、不调用付费模型、不写业务状态 |
| 模式评价 | `research/mining/evaluation.py:evaluate_patterns`；保存效应、新颖性、未知、不确定性和补证要求，再分别记录价值不合格与容量暂缓 |
| 执行与恢复 | 现有 `engine`、`monitor`、RQ；`run_kind=mining` 不变，新 `KddPolicy` 进入 v0.3，旧 `MiningPolicy` 默认、序列化和哈希保持 |
| 问题调度 | `investigations/query_policy.py` 与 `investigations/kdd.py` 提供宿主合法动作、固定产物和回执，独立 query-planner 选择下一步 |
| 页面和长期更新 | 复用调查、topics、history、comparison；展示同一保存版本，新证据另存，不追改旧失败或人工判断 |

`MiningResult.data_preparation` 是本次可计算范围，不是完整总体；全部生成候选保留在 `method_results[*].candidates`，顶层 `candidates` 仅含已选。`pattern_evaluations` 与 `selection_decisions` 分开，后者区分 `selected`、`value_excluded`、`capacity_deferred`、`redundancy_deferred`。执行成功、合格输入、探索性入队、模式有支持和科学有效分别记录。

### 四类方向怎样计算

| 方向 | 单位与适用方法 | 不足时的实际边界 |
|---|---|---|
| 科研 | 已确认独立研究 × 条件；未确认时可明确降为文档探索。TF-IDF/NMF 对照、固定向量聚类及有资格的证据评价 | 不同论文不自动算独立复现；每条评价须绑定正确研究，汇总支持/反证还须共同命题对齐，无共同命题只列库存和缺口 |
| 管线 | 项目或原生登记 × 适应证 × 条件 × 观察时间；格局/状态方法和独立图提示方法 | 登记号不是药物项目；同版本的不同条件行不能当作前后变化，单版本明确历史不足；待审图不入项目或药效分母 |
| 商业 | 有来源资格的企业 × 指标 × 可比期间；同口径数值变化 | 先按币种、单位、地区、人群、报告范围和真实期间跨度/位置分序列，再比较；不按 FY/FP 猜可比性，全年、单季、半年不能混比 |
| 公共卫生 | 地区 × 指标 × 期次 × 人群；合格数值变化，或原生通报/公开期次的描述方法 | 无合格数值仍可计算真实通报；地区、病种、月份不明保留未知。年份不能补成一月，通报增加不等于发病增加 |

数值只采用带出处定位与固定版本的 typed `MetricObservation`，不从正文任意正则抽数字。SEC 原生 entity-wide 披露口径单独标明，合并范围变化未知仍保留。同比/环比描述不自动校正季节或一次性事件。无总体分母不算总体率，没有检验设计不宣称统计显著。

科研向量按模型、版本、维度分空间，缺向量原件留在数据集中并记录方法资格。TF-IDF 的 `processed_unit_ids`、`fit_unit_ids` 与向量各 `model_spaces[*].processed_unit_ids` 可核实际参与范围；双方单位不同就分开报告，不能声称同条件优于基线。没有时间基准的库存探索不编造新颖性距离；单文档内容补证明确是探索假设，不能写成已获支持的模式。阈值冻结在 `ValuePolicy`，不为提高入选数调整。

### 新来源正文与 WeKnora 特征

显式 KDD 来源投影采用 Fabric 固定 `clean_text`，旧未配置来源沿用原摘要优先路径。特征接口必须确认成员的 source/source_record/version、原文与清洗文本哈希，以及模型、维度、分块和索引就绪身份；不能拿返回的 feature.text 覆盖原件正文。监测按真实来源与方向分组读取全部固定成员，采用后持久化派生快照与回执；恢复复用该采用版本，不每轮重复取特征。失败、未返回或无向量成员保留原件和明确缺口。

检索与批量特征是两条用途不同的接口。WeKnora Agent 不成为第二个总调度器；原件仍回 Fabric 读固定版本。上传、索引完成、正文版本绑定和可用于算法分别确认；更正、撤回和撤权继续影响新采用与展示。旧分析保留当时依赖，不能悄悄换成新索引或当前图。

### v2 调度和独立专业 HTTP

新 external v2 可选择 `dataset_prepare`、`analysis_run`、`professional_assess` 及原有文档/图取证动作。每次真实执行后保存产物身份/版本与费用，再让策略观察实际回执；本地加工、计算各计一次工具、零模型调用。没有产物不能把预测 covers 变成已完成。旧 baseline 保留原模型结构、顺序和恢复规则，新增动作空间的效果另列，不冒充同候选范围优势。

MechEvidence 与 BioCheck 的算法、提示和解析留在各自工程，通过独立 HTTP 的 capabilities/execute 继续执行纯方法。专业服务请求模型时返回稳定操作/步骤身份，由 Radar 统一模型回调执行，保存原请求、真实用量和回执后交回，不在专业服务另持模型密钥或隐藏模型重试。HTTP 传输次数与模型次数分开计入统一预算；结果未知保守预留，已收到的专业/模型回执恢复不新增付费调用。HTTP 故障不会自动切回本地。`local` 仅是显式旧兼容模式。

图在数据关联、纯算法提示和调查补证中使用；只有真实固定包和可用工具才能形成候选。规则确认的原生登记关系可进入登记队列，待审关系保持假设，PrimeKG 背景不能独立证明临床疗效或机制因果。历史时点不使用后来图/映射回填过去。

### 本轮真实输入与验收范围

完整固定输入为临床登记 12 份、Europe PMC 10 份、4 家公司的 SEC 5 份、WHO 8 份，分别通过现有快照/运行 HTTP 入口与 RQ 完成计算并保存方法版本。它们不是 35 个独立研究，也不是四方向的总体。自动监测窗口与显式采用完整队列分别验收：早期 SEC 字节截断及旧管线跨条件时间比较的失败保留，新版本正常建立新运行，不改旧结果。

真实成稿和专业核验另看总账：科研报告曾因 `method_input_invalid` 阻塞，WHO 报告保留 FAIL；不能将计算完成、正文一致或页面通过写成科学结论通过。新 external v2 在 `progress.material_scope` 单独显示固定资料与实际片段阅读范围，已有 WHO 八件报告的范围例为固定 8 版、读取 5 版的选定片段、未读 3 版和 2 次补查未完成。Markdown 将系统记录前言放在逐字未改的已核 `final_text` 之外，不把前言冒充已核正文；无 scope 的旧版仍原样导出。`scripts/kdd_e2e.py` 只 GET 已批准的真实运行、原件和报告，不发新模型请求；离线 UI/边界 controls、受控 PG/RQ 与真实专业报告分别列出。

后续各方向仍需多案例、正反例、未入选抽查、连续新增/更正/撤回与独立价值评价。后来 labels 仅用于评分，不进模型；冻结时点、拟合成员、方法与阈值，误报漏报只在实际审查范围内报告。某方向通过不替别的方向背书，`unsupported`/未知不算通过，也不阻止其他有资格方法继续计算。

```bash
cd /home/zk_test/zk_projects/BioRadar
COMPOSE_PROJECT_NAME=bioradar-zktest make init
```

宿主机的 Python 3 只负责安装工具；`make bootstrap` 由 uv 准备项目独立的 Python 3.12 和锁定依赖，不改变 Data-Fabric 的环境。前端构建使用 Node 22 容器。服务器保留公共基础镜像缓存，项目仍在 zktest 从源码构建。

API 默认地址为 `http://127.0.0.1:18100`，Web、数据库和 Redis 的端口由 `ops/.env` 配置，服务都只监听服务器回环地址。目前仅允许 development/test。网页写操作检查允许来源，修改浏览器访问地址时须一起核对服务配置。

本地研究凭据保存在 `ops/.env` 的 `ENGINE_DEV_CREDENTIAL`，与上游 API key 分开。命令行通过本地凭据访问 API，网页换取短期会话；凭据不写进命令输出、文档、截图或浏览器存储。交付包不带本机的 `ops/.env`、SSH 配置、真实资料、虚拟环境或工作目录。

### 三个独立服务的部署模板

本轮新增六个 ops 文件：`ops/biocheck.env.example`、`ops/mechevidence.env.example`、`ops/weknora-kdd.env.example` 和 `ops/systemd/` 下同名的三个 `bioradar-*.service`。继续使用既有 user systemd、PostgreSQL 和 Redis，不新增平台；这些文件是可审阅部署模板，不表示已在现役全部启用。

### 计算和补录的限制

默认每次最多取 50 个新版本、保留 2000 条特征记录；按字节上限排除的记录会说明原因，原始版本仍留在 Fabric。一个窗口不是全库，更不是某领域完整分母。现有方法在输入满足时计算，缺身份、时间或分母时保留缺口。

默认每批最多调查 2 条、每小时最多 6 次，同一普通线索冷却 60 分钟；每次补查最多 2 个问题、每问最多 3 条资料。延期线索保留，预算和冷却不是删除理由。调参先看有效线索与人工审阅能力，不只看机器能跑多快。

普通雷达发现与长期专题共用调查额度。两边都有可执行待办时轮流取得新额度；另一边没有合格任务时可以用完剩余额度。暂停、已关闭、旧范围和失去许可的任务不占位。同一任务中断后按原回执继续，不重复扣额度。

Fabric 的 `--batch-size` 控制处理待办数量，`--backfill-batch-size` 单独控制旧库存补录，设为 0 可停补录。不要把两者设成同速后让旧库一直制造积压。当前盘剩余空间有限，发布保留至少 15 GiB；不足时停新增复制，已成功保存的固定回执仍可确认。扩大旧库处理量之前，先测原文、清洗结果和索引合计占用。 zktest 首批实测后，当前采用每 10 秒补录最多 5 条、处理最多 20 项待办；雷达每 2 秒轮询一个来源。来源数、补录量和计算用时都会影响一轮耗时，不保证秒级完成。机上调速放在 publisher 的 systemd override，代码中的保守默认值保留。

## 从一个问题开始研究

以 Elranatamab 的机制与临床证据为例，先核对原件，再追问是否能外推到一线治疗。初次查询、补查、模型步骤、机制评价和最终报告都在这项调查里。追问保存自己的问题和父版本，旧报告保留。

### 谁决定下一步查什么

提问时可选 baseline 或 query_planner。baseline 保留原来的查询顺序、一次减词和一次 WeKnora 补查，用作比较。query_planner 每次在当前允许的动作中选一项，执行后把真实结果交回策略，再决定下一步。

一次动作留下四件事：为什么选它、实际查了什么、拿回哪些固定原件、下一步据此怎样决定。预计能补上哪项资料，只是选动作的理由；有原件并解释它如何覆盖问题，才能标为已覆盖。管线布局分别检查支持、反证、竞争、类似失败、技术与专利，缺项留在报告中。

MechEvidence 的反向观察和缺失实验进入后续查找。BioCheck 完成正文核验与所选片段复核后，给出可修改位置和材料缺口。雷达最多因这轮质量反馈再补查一次；有新原件或有效证据片段选择变化才重做相关研究与报告，无预算或无新材料则保留已核稿，写明缺口。修过的文字重新核验。

PrimeKG 先查实际对象名称。唯一匹配才能带着返回的真实标识取得关系资料；多个匹配或没找到时保留待辨认。当前图查询与固定图版本分开，图背景用于提出问题，不自动计为药效证据。

### 中断、超时和质量检查怎样处理

研究过程使用已有数据库和队列保存进度。模型回执已经保存时，恢复任务直接使用该回执，不再请求一次；即使总时限已经结束，也可以把已完成的报告保存下来。当前来源许可仍须有效。

如果时间在“准备发送”的记录落库期间耗尽，请求尚未发出，调用记录明确记为未发送。请求已经发出但结果不明，则保留未知状态，不能自动重发。可选修订或复查没有足够预算时，交付已经核验的原稿；未经复查的修订稿另存，不能代替原稿。

潘的全文核验与所选引用片段复核分别保存。比如正文说对了，但引用选择了不支持这句话的段落，页面要显示“所选支持片段待核”。这不应触发对正确正文的自动改写。全文核验器自己返回了不存在的段落位置时，也先保留原稿和错误，不据此修订。

相关定位检查在 `tests/test_biocheck_coordination.py`、`tests/test_biocheck_support_audit.py`、`tests/test_research_recovery_faults.py` 和 `tests/test_weknora_fixed_identity.py`。故障测试复用 PostgreSQL、RQ 和本地计数服务，不向商业模型发送付费请求。历史真实研究与本次回读分别记录在 `evaluation/handoff-verification.json`。

### 本次研究的预算

本轮 KDD 隔离运行采用单任务最多 24 次模型请求、524288 token、1800 秒、12 次查询、64 次工具调用，单次输入上限 131072 字节、输出上限 32768。持久配置的手工分析与材料更新合计每小时 2 次；monitor 新线索另限每小时 1 次、每批 1 次。MONITOR、AUTO 与 SEMANTIC 已在同一隔离配置开启，既有任务保留准入时冻结的预算；这些配置不改写现役主目录的历史设置。前端可以调低，不能调高服务器上限。各阶段和专业方法共用这份账；模型服务的单次输出、输入长度和超时限制继续有效。

实际模型回执提供 token 时按回执计数；完整响应没有用量时以有标注的上界估算扣减。已经发出但结果不明的请求保留记录，不自动重发。检索服务没有返回费用时明确记录用量未知，查询次数照常计算。后台调查每小时额度与单次研究预算是两层限制。

若任务停下，先看停止阶段和错误：没有材料需要改查询或补来源；来源失败查对应接口；预算不足可以明确发起新尝试，旧尝试保留。不要清空队列、改旧结果或重复点提交来掩盖失败。 待核、失败或阻塞稿可点“重新研究”。这些操作明确创建新尝试，沿用原问题和原父版本，旧结果保留；后台不会因核验未通过就自动反复付费。

脚本只提交问题和追问，不插入证据或模型答案。它检查真实查询、实际调用、最终报告、两种导出和旧版保留。输出保存实际结果，已存在的文件不会覆盖。失败后先读结果文件和任务状态，再决定是否发起新尝试。测试服务用完关闭，15176 不设为常驻网页。

### 本轮回退

本轮复用原有表与 RQ 队列，没有新增业务数据库迁移。新分析记录使用 v0.5，旧代码未必认识新增报告和查询字段；回退执行逻辑时应保留新记录的读取兼容。修改通过普通 Git 提交保存。需要停止新的专业调用时，可以先停用相应目录配置，保留既有资料和报告。

### 运行一次真实有界调查

0.5 的命令从一个明确研究问题开始，只查 Data-Fabric 已有资料，不触发采集、抽取或模型任务。先用标题中的明确词语做 AND 查询，每轮最多取得 6 条候选；再从实际干预名派生最多 2 次查找，共不超过 3 轮、18 条采用材料。范围、未找到、达到上限和读取失败分别保存。

资料采用已有原始协议中的准确字段及其出处，分开记录登记状态、停止原因和日期；程序生成的是事实整理与待核问题，保存为笔记和材料，不自动代写研究人员判断。没有取得某项结果时说明缺少，不能把终止登记直接写成药物失败。

入口为 `services/bioradar/ops/dig.py`。使用已初始化并完成迁移的本项目数据库，只需启动 PostgreSQL；不需要网页、API 或 Worker：

```bash
docker compose --env-file ops/.env -f ops/compose.yaml up -d postgres
BIORADAR_DATA_FABRIC_URL=http://127.0.0.1:8100 \
  .venv/bin/python -m bioradar.ops.dig \
  --request contracts/examples/digging-clinicaltrials.request.json \
  --output artifacts/digging-result.json
```

输出 JSON 包含每轮查询、逐条字段、差异和缺口，是结构化调查记录，不是自动专业研报。调查材料另存在本项目数据库，可供既有页面或后续导出读取。当前参数文件是明确研究问题的例子，实际命中与判断以本次读取为准。

输出文件已存在时命令拒绝覆盖。中断后先按回执中的 `execution_id` 核对已保存调查，不删除回执盲目重跑；确认需要另一次调查时使用新的输出路径。该命令从 `ops/.env` 读取本项目数据库和来源许可，服务地址仍须显式设置为已核实的地址；与前面的独立资料包读取命令区分。

两条停止类记录的来源理由涉及战略调整；其中 NCT03758417 明确表示与安全、疗效或数据完整性问题无关。结果是否可得仍未知，不能从登记状态推断药物失败。本次保存六条材料，逐条引用与两个派生词的原字段、片段均已核对，未自动保存人工判断，调查暂停等待研究人员继续。再次使用时库中内容可能变化，不把这组数量当作固定正确答案。

#### 在自己的测试环境复现

先准备两个独立 PostgreSQL 数据库和一个独立 Redis。Fabric 历史模块显式设置 `DATAFABRIC_HISTORY_DATABASE_URL`，没有配置就报未接通，不回退到现役 APP.DB_URL。雷达使用 `BIORADAR_DATABASE_URL`。详细来源字段见[接口说明](接口说明.md)。

Fabric 需要 READ_TOKEN、ADMIN_TOKEN、SOURCE_ALLOWLIST、REDIS_URL、DATA_ROOT 五项 `DATAFABRIC_HISTORY_*` 配置；雷达需要 `BIORADAR_DATA_FABRIC_URL`、`BIORADAR_DATA_FABRIC_HISTORY_READ_TOKEN` 与自己的研究登录凭据及来源许可。凭据从私有环境加载，不写入请求文件、命令输出或 Git。

先完成迁移：

~~~bash
# 在 Fabric 工作目录及其 Python 环境，载入独立历史配置后
python -m migration.history

# 在 Radar 工作目录及其 Python 环境，载入自己的独立配置后
python -m alembic -c db/alembic.ini upgrade head
~~~

然后分别启动测试进程。下面端口仅用于本次隔离联调；开发者自行管理启动与停止，不将测试进程作为学生长期服务。

| 进程 | 命令及条件 |
|---|---|
| Fabric API | `python -m uvicorn api.main:app --host 127.0.0.1 --port 18511` |
| Fabric Worker | 在同一配置下启动现有 RQ `extraction` 队列，连接专用 Redis；不接现役抽取队列 |
| Radar API | `python -m uvicorn bioradar.api.app:app --host 127.0.0.1 --port 18510` |
| Radar Worker | `python -m bioradar.ops.worker`，用于已有计算与实际队列检查 |

API/CLI 在宿主机运行时，雷达可访问 `http://127.0.0.1:18511`。普通 Docker 容器里的 127.0.0.1 是容器自己；`make dev` 不会自动接上宿主 Fabric。当前地址校验也只接受回环地址，因此本轮新链仅支持宿主进程联调；普通容器与宿主 Fabric 的接入需另行检查网络和许可配置，不能直接换成网桥地址。

两个 API 和 Fabric Worker 启动后，在雷达环境执行：

~~~bash
python scripts/history_e2e.py \
  --fabric-url http://127.0.0.1:18511 \
  --radar-url http://127.0.0.1:18510 \
  --mode all --output artifacts/history-e2e.json
~~~

此脚本需要同进程环境中的 Fabric 管理员/只读测试凭据及雷达研究登录凭据，**会写入教学资料和研究记录，只对独立测试库运行**。真实公开资料留在受控的运行目录，不提交到教学样例。

脚本分两部分，可分别用 `--mode demo` 或 `--mode public`：

- 教学历史：不同年份各有自己的项目清单；验证晚公开标签不能进入过去训练、后来正文不能覆盖当时版本、未成熟窗口不评分、未知不算失败、后续评分不改原预测。已知例子四个训练项目中两个有事件，基准为 0.5；两条可评价结局的 Brier 为 0.25。这只是工程算术检查。
- 真实公开资料：通过 Fabric API 受理抓取，由实际 RQ Worker 执行、写入 PostgreSQL，雷达通过 HTTP 读取、保存调查并导出。当前公开资料不能凭老日期获得历史回放资格。

脚本结束会给出研究 ID、调查 ID、实际范围和各项检查结果。来源网络失败就报告失败，不退回假数据。核对实际结果后再交接。

## 从图谱开始一次调查

这一条接在清洗资料之后，也可以与文本调查并行。Fabric 负责发布对象、关系和所依据的原文版本；雷达按问题选择邻居、继续查证。唐蔚雯的实体字典、审核和消歧继续是唯一来源，不在雷达里再写一套。

| 要改什么 | 从哪里看 |
|---|---|
| Fabric 当前图与原文的发布、分批读取 | Fabric 的 `flows/graph_publish.py` |
| Fabric 图资料结构、名称匹配、限定邻域 | Fabric 的 `biz_rules/reviewed_graph.py` |
| 雷达如何读取图谱和核对原文 | `services/bioradar/adapters/fabric_graph.py` |
| 选择下一问题、采用材料、提醒复查 | `services/bioradar/research/investigations/graph.py` |
| 选择图资料、输入名称、处理重名 | `apps/web/src/components/engine/GraphInvestigationForm.vue` |
| 两个真实服务一起运行的检查 | `scripts/graph_e2e.py` |

首次准备独立测试环境时，Fabric 运行 `python -m migration.history`；现役已完成迁移，不要求接手时重复执行。V018 只为已有历史表增加 graph 资料类型，不建新图数据库。来源许可需明确包含 `reviewed_graph`、`primekg_graph`、`legacy_documents` 及实际原始来源；许可由管理员配置，不能为了导入方便随意改来源名。雷达不持 Fabric 管理员凭据。

现役原文与审核变化已由发布程序持续处理，不需要每批手工导出。下面两步 CLI 用于隔离验收或明确范围的专项桥接，在 Fabric 环境执行；scope.json 是明确文档 UUID 的数组。执行前核对已有回执，不能把同一原文重发成新独立证据；原文与回执放私有运行目录，不进 Git。

~~~bash
python -m flows.graph_publish capture-legacy \
  --url http://127.0.0.1:8100 --namespace zktest.fabric.tang \
  --scope-file scope.json --output observation.json

python -m flows.graph_publish publish-legacy \
  --observation observation.json --idempotency-key <本次唯一键> \
  --receipt publish-receipt.json
~~~

默认只读人工审核通过的记录。需要研究自动审核结果时，采集命令显式加 `--include-auto-approved`；它们仍保留未确认身份，不混入已确认对象的别名。一次最多六篇是传输批次，不是项目规模上限；续批使用原清单、`--offset` 和首批返回的 `--expected-scope-sha256`。清单变化重新建一批，不沿旧位置接着读。原文保存成功而图发布失败时，先看回执，不能把旧原文删掉重来。

PrimeKG 可用同一工具直接读取，不需要手工拼观察文件。管理员配置独立的 `DATAFABRIC_GRAPH_NEO4J_URL/USER/PASSWORD`（数据库默认 neo4j）；只执行固定的参数化一层查询，不开放任意 Cypher，不修改原图：

~~~bash
python -m flows.graph_publish capture-primekg \
  --node-type gene/protein --node-source NCBI --seed-id 1956 \
  --neighbor-term lung --limit 10 --output primekg-observation.json

python -m flows.graph_publish publish-primekg \
  --observation primekg-observation.json --idempotency-key <本次唯一键> \
  --receipt primekg-receipt.json
~~~

PrimeKG 当前观测用 `publish-primekg` 发布，输入是明确节点范围的实际读取结果。它保留这次真实收到的背景，之后可按首次收到时间回看；不能证明此前的公开可得性。当前图并不补齐过去十年的图谱；以后接历史图快照，需要单独验证当时的对象、关系、别名和证据，不能只补一个日期。

现役历史读取地址是 `BIORADAR_DATA_FABRIC_URL=http://127.0.0.1:18511`，旧临床标题补查使用 `BIORADAR_DATA_FABRIC_RESEARCH_URL=http://127.0.0.1:8100`。隔离环境自行配置不同服务和数据库，不照抄现役地址运行写入脚本。

接唐蔚雯的真实资料时还要核对三个缺口：审核人/审核时间与合并日志尚未完整传出；自动发布检查引文唯一性，旧 CLI 仍取首次匹配；审核变化可能归并为发布时的当前图，并非完整中间沿革。缺信息保持未知，源端补齐后李明洋适配接口，孙博文判断是否够资格进入计算，刘金彦显示实际取得的内容。

网页进入“调查”，选择真实或教学资料、图谱来源和资料版本，再输入对象名及问题。也可用 `python -m bioradar.ops.history_cli graph --input request.json --output receipt.json`；其余连接参数见该命令 `--help`。没有匹配对象、名称重名、邻域为空、查询失败或未找到材料，结果各自说明原因。

独立环境中运行：

~~~bash
python scripts/graph_e2e.py \
  --fabric-url http://127.0.0.1:18511 \
  --radar-url http://127.0.0.1:18510 \
  --real-bundle <实际PrimeKG资料.json> \
  --output artifacts/graph-e2e.json
~~~

该脚本会写测试库，不能对现役库运行。教学部分检查精确引用、方向、新旧图比较及判断复查；真实部分要求图谱确实引出临床查询并采用真实资料，空结果或服务失败不能冒充完整通过。图谱采用结果仍在原调查页面阅读，不需要另开图谱工作台。

## 改完代码怎样生效

BioRadar 主线为 `main`。本轮直接在雷达主线提交，更新了后端、页面、接入配置和文档，已重启雷达 API、Worker、Monitor；没有新增业务数据库迁移。Data-Fabric 继续由其维护者负责。后续从主目录最新提交接续，不按每轮版本新建交付分支。开始前核对学生的新提交和未提交修改。

zktest 当前使用本文件前面的 systemd 运行方式：先在独立测试环境验证，更新主目录，运行必要的兼容迁移，再重启受到影响的服务。修改 Python 后端后，已有 API、Worker 和 Monitor 进程不会自动加载新代码。`make web-check` 生成类型并构建页面；网页调试由学生按需启动，不随六个后台服务常驻。

`make dev` / `make stop` 是另外保留的独立 Compose 开发方式，不是现役 systemd 服务的启停命令。现役服务已经启用用户级开机恢复，具体状态以 `systemctl --user status` 为准。

日常代码更新用 Git 提交记录；涉及数据结构变化或批量改写时，再准备相应的数据备份与恢复步骤。代码回退用明确的 Git 提交，保留数据库卷和新增历史表；先停新任务，再回退受影响代码，不通过删表“还原”。回到不认识 graph 类型的版本前，先停图发布并调整旧代码的来源许可。新增专题表同样保留，旧代码可以不使用它们。迁移的兼容性逐项检查，不执行 `down -v`。首次交付的 `baseline/bioradar-v0.4` 和 `handoff/zktest-20261016` 标记继续保留。

## 检查和运行问题

| 改了什么 | 怎么检查 |
|---|---|
| Python 业务逻辑 | 运行对应测试和 `make lint`，检查一个正常行为及相关错误行为 |
| 接口字段 | `make engine-contract` 导出，再 `make web-check` 生成类型和构建；不手改生成文件 |
| 数据库和后台运行 | `make engine-integration` 使用本地 PostgreSQL；`make smoke` 检查实际数据库与后台执行 |
| 页面 | `make web-check`；切换记录、保存、刷新、退出时实际操作一次 |
| 文档 | 核对链接、操作步骤和实现状态，不重复跑与文字无关的测试 |

代码交付前统一执行 `make test CARD=BOOT`、`make contract-check`、`make lint`、`make web-check`；数据库或队列有变化时执行 `make smoke`。数据库测试出现 skip 说明没有实际检查相应环境。

本次交接的检查结果保存在 [工程检查记录](../evaluation/handoff-verification.json)，包含代码审查、实际操作范围和仍未接通的服务。

应用版本、挖掘计算版本和决策计算版本分别维护。计算含义改变时升级相应版本，保留旧输入和结果。只保存调查笔记不需要改算法版本。

现役运行问题先看 `systemctl --user status` 和对应服务日志；独立 Compose 环境再使用 `make status`。Redis 暂不可用时，已受理的计算仍在数据库。恢复同一服务后，可以使用已有恢复入口：

```bash
docker compose --env-file ops/.env -f ops/compose.yaml exec -T api \
  python -m bioradar.research.engine.recover --limit 100
```

现役进程使用前文的 systemd 命令停止；独立 Compose 环境使用 `make stop`，均保留数据库卷。不要为调试雷达而清理上游数据或重启共享平台。调查记录直接保存在数据库，不需要另外启动一种后台作业。

## 长期观察怎样形成情报

先定一个能影响研究或决策的问题，再持续保存它的资料。例如“这一类技术是否已具备值得投入验证的证据”，比“每天写一份生物医药日报”更适合作为长期任务。

资料进入后分三步：整理到相应对象和时间，说明与上一版相比变了什么，再判断需要核实哪个问题。报告只是把这段过程交给人阅读的一种形式。没有足够依据，记录可以长期保持资料不足；真正重要的修订应保留旧判断和导致修订的新依据。

| 变化 | 为什么值得看 | 不能直接推导什么 |
|---|---|---|
| 正常的临床、审批或交易节点 | 即使没有异常，也可能改变时间表或竞争条件 | 登记终止不能直接解释为疗效失败 |
| 连续几个周期的变化 | 提示一个持续现象，需要检查同口径资料和原因 | 报道增加不等于行业进入上升周期 |
| 多项独立证据逐渐积累 | 可能改变某个判断的证据基础 | 多个网站转载不等于多次独立复现 |
| 反面结果、更正和撤回 | 可能让旧判断需要复查 | 一条反例不一定推翻所有适用条件 |
| 到了计划节点仍缺更新 | 值得核实计划是否变了 | 没采到资料不等于事件没有发生 |
| 新对象或少见组合出现 | 提供新的调查方向 | 共现不等于机制关系、因果或投资价值 |

管线按试验与项目的实际身份区分；商业数值要核币种、期间和合并范围；疫情资料要核地区、人群和检测口径；科研材料要处理同研究的多版本、转载和反证。方向标签只是整理方式，不能代替这些条件。

本次对照 Palantir，需要同时看[数据处理中调用 LLM](https://www.palantir.com/docs/foundry/pipeline-builder/pipeline-builder-llm)、[对象与业务逻辑](https://www.palantir.com/docs/foundry/architecture-center/ontology-system)、[AIP Logic 的模型与工具调用](https://www.palantir.com/docs/foundry/logic/blocks)、[自动触发分析及处理建议](https://www.palantir.com/docs/foundry/logic/aip-logic-integration-automate)和[AIP Evals](https://www.palantir.com/docs/foundry/aip-evals/overview)。公开设计把语义模型、确定性函数、对象上下文、行动及评测组合起来；不能仅实现对象变化触发，就称已经复刻它的研判能力。公开文档说明的是平台能力，不证明已内置适合本院的医药判断标准。

对应本工程，通用事实抽取和身份对齐复用 Fabric、唐蔚雯的图谱；取证复用 WeKnora；专业评价和生成核验接汪鑫怡、潘倩。研究问题、材料对命题的意义、替代解释、下一步查什么及为什么修改判断，仍由雷达研究逻辑负责。当前固定材料的解读、有限补查、机器分析与更新已接到调查；具体范围见 README。后续接专业课题时替换或增加对应能力，不能用一般模型输出冒充已完成专业评价。

英国政府的[前瞻工具包](https://www.gov.uk/government/publications/futures-toolkit-for-policy-makers-and-analysts/the-futures-toolkit-html)把发现变化、理解含义和选择行动分开；[ICD 203 分析标准](https://www.dni.gov/files/documents/ICD/ICD-203.pdf)要求说明来源、不确定性、假设与替代解释。我们据此把程序观察、待核问题和研究人员判断分开。以上是公开方法参考，不是对商业产品内部实现或效果的证明。

比较效果时，固定同一问题、资料、截止时间、审阅时间和检索预算。记录核实后有用的线索、遗漏、误报、重复、发现时延及每人工小时取得的新事实和反例。抽查未入选资料。只有取得实际 Palantir 环境并做同条件评价，才能称直接产品比较；通过工程测试不能称超过它。

历史回放只使用当时合格的版本和标签。用今天的大模型解释过去资料，模型参数本身可能含后来结局；这只能算回顾性重建。前瞻预测另行固定提交时间和待发生结局，成熟后评价，不能事后挑成功故事。

### 在现有链路上建立专题

打开“长期专题”，选择模板，写清问题、来源和范围后保存。保存只是登记任务，实际读取和计算由已有 `bioradar-monitor` 执行；退出网页仍继续。先看“初始资料是否补齐”，再看观察结果。没有新材料时允许长期维持原判断，不必每天生成报告。

本次部署建立四项真实专题：临床登记、BCMA 与骨髓瘤科研、商业指标、WHO 公共卫生通报。商业专题先等待合格指标，不能用新闻条数代替收入；WHO 通报也不能用于直接计算发病率。新增专题先明确一个问题与来源范围，再扩大到更多赛道。

李明洋维护专题范围、授权与更新频率；孙博文维护什么变化值得追查及其算法；刘金彦维护历次观察、引用回读、导出与验收脚本。修改问题或范围会建立新版本，旧版问题、资料和观察继续可读。

Fabric 的 `DATAFABRIC_HISTORY_WATCHES` 在现役私有环境文件配置固定公开查询，复用 publisher 和原有 RQ，不增开定时平台。目前启用 WHO 最近 30 天更新和 Europe PMC 的 `BCMA AND myeloma` 最近 30 天 `UPDATE_DATE`；每小时开启新一轮，有限页读取通过保存的游标继续。具体范围、是否读完和最后成功时间看 `/api/history/source-health`，不能根据进程在线推断全站已更新。

旧库存按站轮流补录。首次部署由徐子雯在已核对的源库环境执行 `python -m migration.publication --site-index`，只增加 `(source_site,id)` 并发索引，避免每站反复扫描全表。需要撤销这个索引时用 `--drop-site-index`，不删除业务资料。历史库执行 `python -m migration.history`，雷达执行 `alembic -c db/alembic.ini upgrade head`；三者连接不同，执行前必须逐个核对。

### 跑专题验收

后端专项用 `make topics-test`；检查必须连接隔离 PostgreSQL，跳过数据库测试不算完成。端到端脚本通过 HTTP 写入明确标为教学的资料，随后等待真实后台，不直接调用内部计算函数。

```bash
.venv/bin/python scripts/topic_e2e.py \
  --fabric-url http://127.0.0.1:18513 \
  --radar-url http://127.0.0.1:18510 \
  --output artifacts/topic-check.json
.venv/bin/python scripts/topic_sources_e2e.py \
  --fabric-url http://127.0.0.1:18513 \
  --radar-url http://127.0.0.1:18510 \
  --output artifacts/topic-sources-check.json
```

两端凭据按脚本中的环境变量提供，不写进命令。以上地址是本次隔离测试入口，不是常驻服务地址；脚本运行前会核对真实数据库和教学范围。领域脚本中的 WHO 部分要求隔离历史库已有真实、非教学的 WHO 版本，与合成商业、病例、登记数据分开验收。

专题上线前已备份两端数据库与私有配置。暂停单个专题可在页面操作；要回退整次专题改动，先停 monitor、publisher 和相关 worker，核对队列里的任务，再用 Git revert 回退相应提交并恢复原配置。新增表和历史记录保留，不用降级删表。恢复数据库只用于明确的数据损坏，不能覆盖上线后新增资料。备份位置与旧提交见集中验收记录。

## 检查研究结果是否有用

刘金彦负责评测工具，导师或独立研究人员提供专业判断。固定相同资料、截止时间、候选审阅数量和研究时间，比较普通问答、现有知识库和雷达。除了已选线索，还要抽查未选材料，记录漏报、误报、重复、反例遗漏和实际耗时。

开发数据与最终评价数据分开，同一研究的转载或不同版本不能分散到两边。历史回放只使用当时可获得的资料；当前填写的决策假设不能伪装成过去已经知道。代码检查验证程序行为，真实战略效果另行评价。

## 仓库怎么安排

建议在研究院统一的 Git 组织下，保留四个产品仓库。本次已在 zktest 建立独立的 BioRadar 仓库，其余工程没有搬动或合仓。

| 仓库 | 放什么 | 怎样分工 |
|---|---|---|
| BioRadar | 雷达后端、Vue 页面、运行配置和本项目文档 | 按现有李明洋、孙博文、刘金彦的目录归属 |
| Data-Fabric | 采集、清洗、资料版本、数据接口，以及现有身份和图谱模块 | 徐子雯维护数据生产与服务，唐蔚雯维护身份、关系和图谱投影；在同仓按模块分工 |
| WeKnora 定制版 | 现有问答、检索与调度修改 | 李明洋维护，保留与开源上游同步的条件 |
| CPUBrain | 现有科研执行和工作流 | 保持现有维护、运行和发布方式 |

同一产品的前后端放在一起，方便一次修改一起检查。仓库和部署不是一回事：同仓可以有 API、Worker 两个进程；不同仓库也可以在一台开发机联调。跨产品通过接口交换，服务只写自己负责的数据，不通过合仓获得任意写其他数据库的权利。

潘倩、汪鑫怡先保留现有原型，各交付清楚的专业能力模块和调用样例。需要独立部署、共享依赖或共同发布时再确定服务仓库，不按学生人数先建一批平台。Data-Fabric 也不因徐子雯和唐蔚雯分工就复制成两套主数据工程。

李明洋统筹以下几件事，各仓库维护人负责自己的改动：

- 为每个目录登记维护人，重要分支经过审阅和必要检查后合并。使用 GitHub 时可用 [CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners) 指定目录审阅人。
- 接口由提供服务的仓库维护唯一版本，下游固定版本生成类型；跨仓修改分别提交，安排兼容过渡。不要复制几份接口定义后各改各的。
- 在 BioRadar 现有 `ops/` 中记录一组能共同运行的服务版本和联调命令。它只是部署记录，不发展成新的业务平台，也不把其他工程源码塞进去。
- 当前以 zktest 上已确认的 Data-Fabric 版本联调，记录实际提交；环境差异用配置表达。已有本地修改先整理为可审阅提交，其他机器不在本轮修改范围。
- 数据、模型文件和凭据留在相应存储与配置中。项目内复制的其他工程先查清实际依赖，改用明确版本的服务或依赖后，再移除重复源码。
