## 持续运行与维护

自动链路已经有独立后台入口，学生不必再写一个“定时提问”的脚本：

1. Fabric 在原采集库提交时写入 `publication_outbox`。触发器只记录变化，不联网、不跑算法。
2. `flows/history_publish.py` 保存原文版本，发布成功后确认原待办；先处理新变化，旧库存按小批补录。
3. 雷达 `bioradar.ops.monitor` 读取已提交版本，保存本批输入，交给已有 RQ Worker 计算。
4. 孙博文的 `research/monitor/` 选择候选、控制调查预算、补查相关资料。结果追加到已有调查模型，当前来源许可仍逐次核对。
5. 页面 `MonitorPanel.vue` 读取状态与结果，不能把刷新页面当成启动计算。

维护边界：李明洋负责进程、迁移、连接和 adapter；孙博文负责候选、补查和状态推进；刘金彦负责页面、端到端例子与结果检查。徐子雯维护源端待办、版本发布与来源清洗。没有第二套消息队列。

### zktest 的进程

后台采用 user systemd，用户已启用 linger，退出 SSH 后继续工作，主机重启后恢复。单位文件随代码保存在两个仓库的 `ops/systemd/`。只用这一套进程监督，不同时启动 Compose 的 API、worker 和 monitor。

| 服务 | 用途 |
|---|---|
| `datafabric-history` | 本机历史读取接口，18511 |
| `datafabric-publisher` | 把原采集库的已提交变化发布到版本库 |
| `datafabric-history-worker` | 处理已有公开抓取队列，独立 Redis 4 号库，不重复原采集队列 |
| `bioradar-api` | 雷达本机 API，18100 |
| `bioradar-worker` | 执行已有计算队列 |
| `bioradar-monitor` | 持续读变化、组织计算和调查 |

原 Fabric 8100 和原采集进程继续使用；不因雷达运行再启动一组采集 worker。PostgreSQL、Redis 使用原 Compose 项目与数据卷，启用容器重启策略。15176 网页服务保持关闭，学生需要页面时自行启动。

环境配置分别放在 `~/.config/datafabric-publication/runtime.env` 和 `~/.config/bioradar/runtime.env`，权限 600，不提交 Git。原采集库、历史版本库和雷达业务库是不同连接；不得把迁移直接指向猜测的默认库。

常用命令：

```bash
systemctl --user status datafabric-publisher bioradar-monitor bioradar-worker
journalctl --user -u bioradar-monitor -n 40 --no-pager
systemctl --user restart bioradar-monitor
```

暂停自动调查用页面的“暂停后台读取”，状态保存在数据库，重启仍暂停。已经提交的计算会正常收尾，Fabric 仍继续保存资料。停整个数据链时先停雷达 monitor，再停 Fabric publisher；不要清空队列或删表来“重来”。

来源暂时断开和 Redis 暂不可用会按原记录恢复。明确阻塞的批次先查原因，再用 `python -m bioradar.ops.monitor --retry-batch <批次ID>` 恢复同一批；命令必须使用运行服务相同的环境文件。它核对原输入和回执，不重新抽一批资料、不跳过处理位置。

### 计算和补录的限制

默认每次最多取 50 个新版本、保留 2000 条特征记录；按字节上限排除的记录会说明原因，原始版本仍留在 Fabric。一个窗口不是全库，更不是某领域完整分母。现有方法在输入满足时计算，缺身份、时间或分母时保留缺口。

默认每批最多调查 2 条、每小时最多 6 次，同一普通线索冷却 60 分钟；每次补查最多 2 个问题、每问最多 3 条资料。延期线索保留，预算和冷却不是删除理由。调参先看有效线索与人工审阅能力，不只看机器能跑多快。

Fabric 的 `--batch-size` 控制处理待办数量，`--backfill-batch-size` 单独控制旧库存补录，设为 0 可停补录。不要把两者设成同速后让旧库一直制造积压。当前盘剩余空间有限，发布保留至少 15 GiB；不足时停新增复制，已成功保存的固定回执仍可确认。扩大旧库处理量之前，先测原文、清洗结果和索引合计占用。 zktest 首批实测后，当前采用每 10 秒补录最多 5 条、处理最多 20 项待办；雷达每 2 秒轮询一个来源。七个来源的一轮约 14 秒，后续计算、补查仍需实际执行时间，不保证秒级完成。机上调速放在 publisher 的 systemd override，代码中的保守默认值保留。

### 复现自动链路

使用三个隔离测试数据库：原采集表、Fabric 历史库、雷达库；服务只绑定回环地址。先迁移、启动 publisher、两端 API、Worker 和 monitor，再运行 `scripts/monitor_e2e.py`。所需凭据通过环境变量提供。

```bash
.venv/bin/python scripts/monitor_e2e.py \
  --fabric-url http://127.0.0.1:18511 \
  --radar-url http://127.0.0.1:18510 \
  --source-database fabric_source_integration \
  --namespace synthetic.integration.monitor \
  --output artifacts/monitor-check.json
```

脚本在上传前核对服务返回的真实数据库名、教学标识和命名空间，不允许只因地址是 localhost 就写测试资料。它只通过 Fabric 上传；不调用雷达“运行分析”或“开始调查”。检查源端自动发布、实际队列执行、补查原件、重复写入、暂停与恢复，以及第二批自动推进。

本轮真实库曾把采集文件头和 HTML 表格标签当作文本特征。Fabric 正文投影已修正为 v0.2；首批 103 份原件重新投影，原始内容和旧结果保留。三个确认的误报调查已关闭并说明原因，四条尚未执行的表格标记候选已隔离；正常正文候选继续处理。这些记录用于检查误报，不算有效情报成果。

单条原件过大或输入格式不合格时，Fabric 保存明确的字段、上限和单位，保留原待办，延长到一小时后再核对。页面把待处理、重试与已发布分开显示。原件没有发布成功就不算进入雷达；扩大上限前先完成存储与分段读取，不能简单删除长度检查。

### 回退

代码用普通 Git 提交回退，数据库的原文、待办、调查和处理位置保留。若需停止新链路，先停 `bioradar-monitor` 和 `datafabric-publisher`，再按 Fabric README 停用四个源表触发器；回退旧代码前一并核对同文档写入保护。不要 `down -v`，不要删除待办或逆向删除历史表。

本轮合并前的主目录提交记录在 `evaluation/handoff-verification.json`。实际回退由李明洋执行并记录原因，不能在学生有未提交改动时强行 reset。

## 跑一次例子

启动后执行：

```bash
make example
```

命令通过实际接口和后台计算建立一项教学调查：初始线索、五条采用材料和前后两次研究人员判断。每次运行新建一项调查，资料和同条件计算可以复用。结果位置记录在 `artifacts/example.json`，其中不含登录凭据。命令执行不需要打开浏览器；需要逐项阅读或打印时可使用已有调查页面。

例子用的是明确标为测试的材料，作用是解释程序怎样运行，没有生成真实医学或投资建议。所有文字判断由示例脚本明确填写，不是模型评价。

如果自己操作导入，文件选择器读取的是自己电脑上的文件；先取回 `contracts/examples/` 中相应教学文件。也可以直接运行上面的 `make example`，不需要手动上传。

自己操作时：

1. 在“情报雷达”导入 `contracts/examples/engine-fixture.snapshot.json`，选择该资料并运行分析。计算条件可参考同目录的 `engine-fixture.policy.json`。
2. 打开“规范实体组合：K”线索，填写研究问题，保存为调查。
3. 打开调查，选择已经采用的资料，加入材料、分类和说明；保存一次研究人员判断。
4. 再加入一条反面材料，查看待复查提示。记录第二次判断，检查第一版和它当时采用的依据仍在。
5. 刷新页面、暂停或继续调查，最后打印已保存的研究记录。

资料更新例子使用 `engine-fixture.snapshot.json` 与 `engine-fixture-v2.snapshot.json`。页面中选择这两份资料比较，可以看到一条新增、一条内容变更、十四条内容相同、一条本批未出现。新增项是旧资料补录；其中一条内容相同的记录只补充了身份信息。两者都不能当作新近独立研究。

## 接真实资料

采集、清洗和来源版本继续由 Data-Fabric 维护。李明洋先确认现役地址与来源许可，再使用现有读取命令。记录名单是一个 JSON 字符串数组，当前一次最多 20 条：

```bash
.venv/bin/python -m bioradar.ops.snapshot_data_fabric \
  --source-instance datafabric-test \
  --manifest <记录名单.json> \
  --output <采用资料.json>
```

在 zktest 宿主机执行前设置 `BIORADAR_DATA_FABRIC_URL=http://127.0.0.1:8100`，指向同机 Data-Fabric。不要把这个地址用于容器内调用。服务地址从该环境变量读取，来源许可按 `BIORADAR_ENGINE_SOURCE_ALLOWLIST` 和 `BIORADAR_ENGINE_SOURCE_ID_ALLOWLIST` 配置；默认仅包含已有教学来源和核对过的 ClinicalTrials 来源。配置由李明洋维护，页面不能自行扩大许可。这个宿主命令不会自动读取 `ops/.env`；若修改了许可，执行时须同时设置对应 `BIORADAR_ENGINE_*` 环境变量，与 API 保持一致。默认研究空间和 ClinicalTrials 许可已匹配。

当前读取一批资料完整成功才输出资料包；失败直接报错，不输出空包，也不覆盖以前的资料。两批比较只处理已经成功采用的内容，不能判断某条未出现记录究竟是未选择、没读到还是已删除。连续更新使用下述版本发布与 monitor，旧独立导入命令不承担持续读取。

真实材料放在本地受控位置，不进入教学示例或公开分发包。此前三个真实摘要验证了接入和引用；下面的 0.5 例子进一步运行了实际查询和派生查找。两者都不代表已验证一个研究方向。

### 运行一次真实有界调查

0.5 的命令从一个明确研究问题开始，只查 Data-Fabric 已有资料，不触发采集、抽取或模型任务。先用标题中的明确词语做 AND 查询，每轮最多取得 6 条候选；再从实际干预名派生最多 2 次查找，共不超过 3 轮、18 条采用材料。范围、未找到、达到上限和读取失败分别保存。

资料采用已有原始协议中的准确字段及其出处，分开记录登记状态、停止原因和日期；程序生成的是事实整理与待核问题，保存为笔记和材料，不自动代写研究人员判断。没有取得某项结果时说明缺少，不能把终止登记直接写成药物失败。

入口为 `services/bioradar/ops/dig.py`。使用已初始化并完成迁移的本项目数据库，只需启动 PostgreSQL；不需要网页、API 或 Worker：

```bash
docker compose --env-file ops/.env -f ops/compose.yaml up -d postgres
BIORADAR_DATA_FABRIC_URL=http://127.0.0.1:8100 \
  .venv/bin/python -m bioradar.ops.dig \
  --request contracts/examples/digging-clinicaltrials.request.json \
  --output artifacts/digging-result.json
```

输出 JSON 包含每轮查询、逐条字段、差异和缺口，是结构化调查记录，不是自动专业研报。调查材料另存在本项目数据库，可供既有页面或后续导出读取。当前参数文件是明确研究问题的例子，实际命中与判断以本次读取为准。

输出文件已存在时命令拒绝覆盖。中断后先按回执中的 `execution_id` 核对已保存调查，不删除回执盲目重跑；确认需要另一次调查时使用新的输出路径。该命令从 `ops/.env` 读取本项目数据库和来源许可，服务地址仍须显式设置为已核实的地址；与前面的独立资料包读取命令区分。

10 月 16 日已在 zktest 完成一次真实运行：首轮 `BCMA + myeloma` 返回并采用 6 条，`has_more=true`；从原始干预名抽出的 `LCAR-B38M`、`LCAR-BCX` 两轮各返回 1 条已采用记录，没有新增。六条登记的状态为 TERMINATED、WITHDRAWN 各一条，UNKNOWN 三条，RECRUITING 一条，阶段、疾病与干预字段有字面差异。

两条停止类记录的来源理由涉及战略调整；其中 NCT03758417 明确表示与安全、疗效或数据完整性问题无关。结果是否可得仍未知，不能从登记状态推断药物失败。本次保存六条材料，逐条引用与两个派生词的原字段、片段均已核对，未自动保存人工判断，调查暂停等待研究人员继续。再次使用时库中内容可能变化，不把这组数量当作固定正确答案。

重复输出已实测拒绝，原回执与调查版本不变；旧教学例子的五条材料、两版判断仍保留。当时验收结束停止了服务并保留数据卷；本轮新增的持续后台见下节。此次链路是学生继续开发的基础，扩大覆盖、别名处理、专业评价和长期复查仍需接续。

### 新的历史研究链路

本轮新增的链路是：公开接口或历史档案 → Fabric 版本库 → 雷达读取 → 线索计算和限定追查 → 调查保存 → 固定预测 → 后续结局评分。代码与文档都在同一分支 `codex/historical-intelligence`，两库各一份；通过审查后沿原主线交接，运行状态见持续运行一节。

工作目录在 zktest 的 `/home/zk_test/zk_projects/.bioradar-history/`，其中 `fabric/`、`radar/` 分别是两个 Git 工作目录。学生以主目录的当前提交为准，联调工作目录不作为第二条长期主线。测试数据库、Redis、API 与现役环境分开；此处不记录实际凭据。

新数据入口有三种：ClinicalTrials 当前登记、FDA CRL 公开信件、Europe PMC 元数据；历史档案通过 `external_archive` 导入。历史研究与旧 `ops/dig.py` 并存，旧例子仍用原只读临床接口。

主要代码：

| 要改的行为 | 文件 |
|---|---|
| 从 Fabric 分页、核对时间与原文 | `services/bioradar/adapters/fabric_history.py` |
| 研究请求、队列和评价的字段 | `services/bioradar/research/history/models.py` |
| 计算历史事件率和后续评分 | `services/bioradar/research/history/compute.py` |
| 采用资料、追加查找、保存调查与评价 | `services/bioradar/research/history/service.py` |
| 历史研究 HTTP 接口 | `services/bioradar/research/history/routes.py` |
| 命令行创建、查看和评分 | `services/bioradar/ops/history_cli.py` |
| 两个服务一起跑的例子 | `scripts/history_e2e.py` |

只读追查查询的是 Fabric **已经采用的版本**，不是替用户全网抓取。它从已有字段取出真实标识继续查，记录查询范围和新增数量。新站采集由徐子雯的服务独立执行；雷达不持管理员凭据。需要更广检索时接 WeKnora，不能把本地没命中说成全网没有。

#### 在自己的测试环境复现

先准备两个独立 PostgreSQL 数据库和一个独立 Redis。Fabric 历史模块显式设置 `DATAFABRIC_HISTORY_DATABASE_URL`，没有配置就报未接通，不回退到现役 APP.DB_URL。雷达使用 `BIORADAR_DATABASE_URL`。详细来源字段见[接口说明](接口说明.md)。

Fabric 需要 READ_TOKEN、ADMIN_TOKEN、SOURCE_ALLOWLIST、REDIS_URL、DATA_ROOT 五项 `DATAFABRIC_HISTORY_*` 配置；雷达需要 `BIORADAR_DATA_FABRIC_URL`、`BIORADAR_DATA_FABRIC_HISTORY_READ_TOKEN` 与自己的研究登录凭据及来源许可。凭据从私有环境加载，不写入请求文件、命令输出或 Git。

先完成迁移：

~~~bash
# 在 Fabric 工作目录及其 Python 环境，载入独立历史配置后
python -m migration.history

# 在 Radar 工作目录及其 Python 环境，载入自己的独立配置后
python -m alembic -c db/alembic.ini upgrade head
~~~

然后分别启动测试进程。下面端口仅用于本次隔离联调；开发者自行管理启动与停止，不将测试进程作为学生长期服务。

| 进程 | 命令及条件 |
|---|---|
| Fabric API | `python -m uvicorn api.main:app --host 127.0.0.1 --port 18511` |
| Fabric Worker | 在同一配置下启动现有 RQ `extraction` 队列，连接专用 Redis；不接现役抽取队列 |
| Radar API | `python -m uvicorn bioradar.api.app:app --host 127.0.0.1 --port 18510` |
| Radar Worker | `python -m bioradar.ops.worker`，用于已有计算与实际队列检查 |

API/CLI 在宿主机运行时，雷达可访问 `http://127.0.0.1:18511`。普通 Docker 容器里的 127.0.0.1 是容器自己；`make dev` 不会自动接上宿主 Fabric。当前地址校验也只接受回环地址，因此本轮新链仅支持宿主进程联调；普通容器与宿主 Fabric 的接入需另行检查网络和许可配置，不能直接换成网桥地址。

两个 API 和 Fabric Worker 启动后，在雷达环境执行：

~~~bash
python scripts/history_e2e.py \
  --fabric-url http://127.0.0.1:18511 \
  --radar-url http://127.0.0.1:18510 \
  --mode all --output artifacts/history-e2e.json
~~~

此脚本需要同进程环境中的 Fabric 管理员/只读测试凭据及雷达研究登录凭据，**会写入教学资料和研究记录，只对独立测试库运行**。真实公开资料留在受控的运行目录，不提交到教学样例。

脚本分两部分，可分别用 `--mode demo` 或 `--mode public`：

- 教学历史：不同年份各有自己的项目清单；验证晚公开标签不能进入过去训练、后来正文不能覆盖当时版本、未成熟窗口不评分、未知不算失败、后续评分不改原预测。已知例子四个训练项目中两个有事件，基准为 0.5；两条可评价结局的 Brier 为 0.25。这只是工程算术检查。
- 真实公开资料：通过 Fabric API 受理抓取，由实际 RQ Worker 执行、写入 PostgreSQL，雷达通过 HTTP 读取、保存调查并导出。当前公开资料不能凭老日期获得历史回放资格。

脚本结束会给出研究 ID、调查 ID、实际范围和各项检查结果。来源网络失败就报告失败，不退回假数据。核对实际结果后再交接。

#### 自己发起一项研究

历史研究页面支持填写请求，也可以从命令行发起：

~~~bash
python -m bioradar.ops.history_cli create \
  --api http://127.0.0.1:18510 \
  --input request.json --output artifacts/history-receipt.json
~~~

参数含具体来源、截止时间、预测目标、队列回执和训练清单，格式见[接口说明](接口说明.md)。命令先留下回执并保留幂等键；写入结果未知时按回执查询，不删掉回执盲目再发。后续用 `score` 和 `--study-id` 追加评价，`show`、`sources`、`export` 用于读取。具体参数以命令 `--help` 为准。

预测或评价资格不足要看缺口，不能为了让页面出现数值就降低时间要求。真实长期效果需要真实档案和独立专业评价。

## 从图谱开始一次调查

这一条接在清洗资料之后，也可以与文本调查并行。Fabric 负责发布对象、关系和所依据的原文版本；雷达按问题选择邻居、继续查证。唐蔚雯的实体字典、审核和消歧继续是唯一来源，不在雷达里再写一套。

| 要改什么 | 从哪里看 |
|---|---|
| Fabric 当前图与原文的发布、分批读取 | Fabric 的 `flows/graph_publish.py` |
| Fabric 图资料结构、名称匹配、限定邻域 | Fabric 的 `biz_rules/reviewed_graph.py` |
| 雷达如何读取图谱和核对原文 | `services/bioradar/adapters/fabric_graph.py` |
| 选择下一问题、采用材料、提醒复查 | `services/bioradar/research/investigations/graph.py` |
| 选择图资料、输入名称、处理重名 | `apps/web/src/components/engine/GraphInvestigationForm.vue` |
| 两个真实服务一起运行的检查 | `scripts/graph_e2e.py` |

Fabric 先运行 `python -m migration.history`，V018 只为已有历史表增加 graph 资料类型，不建新图数据库。来源许可需明确包含 `reviewed_graph`、`primekg_graph`、`legacy_documents` 及实际原始来源；许可由管理员配置，不能为了导入方便随意改来源名。雷达不持 Fabric 管理员凭据。

旧资料的桥接分两步，在 Fabric 环境执行。下面的 scope.json 是明确文档 UUID 的数组，命令中的文件名由开发者指定；原文与回执放私有运行目录，不进 Git。

~~~bash
python -m flows.graph_publish capture-legacy \
  --url http://127.0.0.1:8100 --namespace zktest.fabric.tang \
  --scope-file scope.json --output observation.json

python -m flows.graph_publish publish-legacy \
  --observation observation.json --idempotency-key <本次唯一键> \
  --receipt publish-receipt.json
~~~

默认只读人工审核通过的记录。需要研究自动审核结果时，采集命令显式加 `--include-auto-approved`；它们仍保留未确认身份，不混入已确认对象的别名。一次最多六篇是传输批次，不是项目规模上限；续批使用原清单、`--offset` 和首批返回的 `--expected-scope-sha256`。清单变化重新建一批，不沿旧位置接着读。原文保存成功而图发布失败时，先看回执，不能把旧原文删掉重来。

PrimeKG 可用同一工具直接读取，不需要手工拼观察文件。管理员配置独立的 `DATAFABRIC_GRAPH_NEO4J_URL/USER/PASSWORD`（数据库默认 neo4j）；只执行固定的参数化一层查询，不开放任意 Cypher，不修改原图：

~~~bash
python -m flows.graph_publish capture-primekg \
  --node-type gene/protein --node-source NCBI --seed-id 1956 \
  --neighbor-term lung --limit 10 --output primekg-observation.json

python -m flows.graph_publish publish-primekg \
  --observation primekg-observation.json --idempotency-key <本次唯一键> \
  --receipt primekg-receipt.json
~~~

PrimeKG 当前观测用 `publish-primekg` 发布，输入是明确节点范围的实际读取结果。它保留这次真实收到的背景，之后可按首次收到时间回看；不能证明此前的公开可得性。当前图并不补齐过去十年的图谱；以后接历史图快照，需要单独验证当时的对象、关系、别名和证据，不能只补一个日期。

雷达与旧临床服务同地址时不需额外配置。隔离联调中，历史服务在 18511、现役临床只读服务在 8100，可单独设置 `BIORADAR_DATA_FABRIC_RESEARCH_URL=http://127.0.0.1:8100`；这只是读取地址，不能指向写接口。

网页进入“调查”，选择真实或教学资料、图谱来源和资料版本，再输入对象名及问题。也可用 `python -m bioradar.ops.history_cli graph --input request.json --output receipt.json`；其余连接参数见该命令 `--help`。没有匹配对象、名称重名、邻域为空、查询失败或未找到材料，结果各自说明原因。

独立环境中运行：

~~~bash
python scripts/graph_e2e.py \
  --fabric-url http://127.0.0.1:18511 \
  --radar-url http://127.0.0.1:18510 \
  --real-bundle <实际PrimeKG资料.json> \
  --output artifacts/graph-e2e.json
~~~

该脚本会写测试库，不能对现役库运行。教学部分检查精确引用、方向、新旧图比较及判断复查；真实部分要求图谱确实引出临床查询并采用真实资料，空结果或服务失败不能冒充完整通过。图谱采用结果仍在原调查页面阅读，不需要另开图谱工作台。

## 改完代码怎样生效

BioRadar 统一以 `main` 作为开发和交付主线，zktest 上的 Data-Fabric 沿用 `dev`。此前临时分支中的已验证改动已经归入主线；本轮按用户要求，两库各用一个 codex/historical-intelligence 临时分支做历史研究联调，审查完成前不覆盖现役目录。正常修改直接形成清楚的提交，不按每次修改、版本或日期另建分支。多人并行确需临时分支时，由李明洋协调，完成后合回主线并删除。BioRadar 尚未配置远端仓库，本轮也未推送 Data-Fabric 的远端。共享运行目录由李明洋统一更新。李明洋合并和检查后执行 `make dev`，重新构建并更新本项目服务；前后端源码改动都通过这条命令发布。`make web-check` 会先安装锁定的前端依赖，再生成类型和构建。

需要使用服务时执行 `make dev`，调试结束执行 `make stop`。本版没有另外配置开机启动服务，服务器重启后不会承诺自动恢复。

保存重要研究记录后，由李明洋在更新前备份 BioRadar 自己的数据库。代码回退用明确的 Git 提交，数据卷保留；本轮新增的 Fabric 历史三表与雷达历史两表均为新增结构；回退代码时先停止对应新任务，保留这些表和原件，再运行旧代码。如果回到不认识 graph 类型的旧代码，先停止图发布，并从旧服务来源许可中移除 reviewed_graph、primekg_graph、legacy_documents；保留这些数据及 V018 扩展，旧四个历史来源继续使用。不要通过降级删表来回退；将来需要删除测试数据时单独处理。涉及其他迁移时检查各自兼容性。`make stop` 不删除数据卷，禁止为回退执行 `down -v`。首次交付有 `baseline/bioradar-v0.4` 和 `handoff/zktest-20261016` 两个 Git 标记。

## 检查和运行问题

| 改了什么 | 怎么检查 |
|---|---|
| Python 业务逻辑 | 运行对应测试和 `make lint`，检查一个正常行为及相关错误行为 |
| 接口字段 | `make engine-contract` 导出，再 `make web-check` 生成类型和构建；不手改生成文件 |
| 数据库和后台运行 | `make engine-integration` 使用本地 PostgreSQL；`make smoke` 检查实际数据库与后台执行 |
| 页面 | `make web-check`；切换记录、保存、刷新、退出时实际操作一次 |
| 文档 | 核对链接、操作步骤和实现状态，不重复跑与文字无关的测试 |

代码交付前统一执行 `make test CARD=BOOT`、`make contract-check`、`make lint`、`make web-check`；数据库或队列有变化时执行 `make smoke`。数据库测试出现 skip 说明没有实际检查相应环境。

本次交接的检查结果保存在 [工程检查记录](../evaluation/handoff-verification.json)，包含代码审查、实际操作范围和仍未接通的服务。

应用版本、挖掘计算版本和决策计算版本分别维护。计算含义改变时升级相应版本，保留旧输入和结果。只保存调查笔记不需要改算法版本。

遇到运行问题先看 `make status` 和对应服务日志。Redis 暂不可用时，已受理的计算仍在数据库。恢复同一服务后，可以使用已有恢复入口：

```bash
docker compose --env-file ops/.env -f ops/compose.yaml exec -T api \
  python -m bioradar.research.engine.recover --limit 100
```

停止本项目使用 `make stop`，保留数据库卷。不要为调试雷达而清理上游数据或重启共享平台。调查记录直接保存在数据库，不需要另外启动一种后台作业。

## 检查研究结果是否有用

刘金彦负责评测工具，导师或独立研究人员提供专业判断。固定相同资料、截止时间、候选审阅数量和研究时间，比较普通问答、现有知识库和雷达。除了已选线索，还要抽查未选材料，记录漏报、误报、重复、反例遗漏和实际耗时。

开发数据与最终评价数据分开，同一研究的转载或不同版本不能分散到两边。历史回放只使用当时可获得的资料；当前填写的决策假设不能伪装成过去已经知道。代码检查验证程序行为，真实战略效果另行评价。

## 仓库怎么安排

建议在研究院统一的 Git 组织下，保留四个产品仓库。本次已在 zktest 建立独立的 BioRadar 仓库，其余工程没有搬动或合仓。

| 仓库 | 放什么 | 怎样分工 |
|---|---|---|
| BioRadar | 雷达后端、Vue 页面、运行配置和本项目文档 | 按现有李明洋、孙博文、刘金彦的目录归属 |
| Data-Fabric | 采集、清洗、资料版本、数据接口，以及现有身份和图谱模块 | 徐子雯维护数据生产与服务，唐蔚雯维护身份、关系和图谱投影；在同仓按模块分工 |
| WeKnora 定制版 | 现有问答、检索与调度修改 | 李明洋维护，保留与开源上游同步的条件 |
| CPUBrain | 现有科研执行和工作流 | 保持现有维护、运行和发布方式 |

同一产品的前后端放在一起，方便一次修改一起检查。仓库和部署不是一回事：同仓可以有 API、Worker 两个进程；不同仓库也可以在一台开发机联调。跨产品通过接口交换，服务只写自己负责的数据，不通过合仓获得任意写其他数据库的权利。

潘倩、汪鑫怡先保留现有原型，各交付清楚的专业能力模块和调用样例。需要独立部署、共享依赖或共同发布时再确定服务仓库，不按学生人数先建一批平台。Data-Fabric 也不因徐子雯和唐蔚雯分工就复制成两套主数据工程。

李明洋统筹以下几件事，各仓库维护人负责自己的改动：

- 为每个目录登记维护人，重要分支经过审阅和必要检查后合并。使用 GitHub 时可用 [CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners) 指定目录审阅人。
- 接口由提供服务的仓库维护唯一版本，下游固定版本生成类型；跨仓修改分别提交，安排兼容过渡。不要复制几份接口定义后各改各的。
- 在 BioRadar 现有 `ops/` 中记录一组能共同运行的服务版本和联调命令。它只是部署记录，不发展成新的业务平台，也不把其他工程源码塞进去。
- 当前以 zktest 上已确认的 Data-Fabric 版本联调，记录实际提交；环境差异用配置表达。已有本地修改先整理为可审阅提交，其他机器不在本轮修改范围。
- 数据、模型文件和凭据留在相应存储与配置中。项目内复制的其他工程先查清实际依赖，改用明确版本的服务或依赖后，再移除重复源码。
