## 开发约定

**先把事情做完**

- 交付单位是用户能完成的一条操作：提问 → 取证 → 报告 → 核验 → 追问或导出。只建接口、写计划不算完成。
- 有合理默认值就继续做；需要外部条件时写清依赖，同时完成不受影响的部分。没做到的写进 README 的「未完成」，写具体原因和下一步。
- 测试数据、真实材料、机器判断和人工决定分开记录。不编造模型调用、研究成绩或接通状态。

**代码要简单**

- 一个 Python 应用（FastAPI + SQLAlchemy + 一个 RQ 队列）、一个 Vue 应用、PostgreSQL、Redis。普通函数优先；不加通用 Agent、工作流平台、第二队列、插件框架、注册中心，也不加没有当前用途的抽象层。
- 哈希只用在三处：Fabric 给的来源版本号、分析输入去重（`analyses.input_hash`）、模型调用幂等。
- 模型输出要小：最多两层、少量必填字段。编号（E1、Q1、F1、A1、句子序号）由程序分配，模型只引用；无效的一条丢掉并记入 notes，不让整份输出失败。结构化阶段（规划、阅读、计算、评估、分诊）关闭思考模式。
- 证据原文只存一次（`evidence` 表），模型调用只记一次（`llm_calls` 表）。progress 里不放请求和原始响应（planner 的决策记录除外，见决策 0013）。
- 雷达不复制专业服务的算法；服务没配置时，对应步骤记为未运行。
- 注释和 docstring 解释代码今天为什么这样，不引用评审轮次或任务编号（决策 0001）。
- 测试覆盖真实错误和容易误伤的正确例子，不写断言手续的测试。

**研究执行**

- 主动提问、追问、专题自动分析、历史回放都走 `research/analyses.py` → `research/pipeline.py`。
- 进度的每个键在 `research/state.py`（RunState）里声明；对外视图只输出标了 SHOWN 的字段，新字段默认不外露。
- 每个阶段结束保存一次进度；中断后从保存的阶段继续，正在进行的那次调用会重发一次（已知成本）。
- 历史回放必须带截止时间；不得用后来才知道的名称或结局作检索词。
- 保留 baseline 作对照，改 planner 方法时不悄悄改 baseline 的顺序和范围。
- PASS 只表示 BioCheck 本次机器核验没发现问题；独立复核、科研结论成立、人工采用是不同的结果，分开记录。

**源码、配置与运行**

- 开始前看 Git 状态，不覆盖别人的修改；正常提交，不强推，不重写历史。
- 凭据、模型密钥只放私有配置（0600），不进代码、报告、前端或日志。
- 测试用独立数据库、Redis 库号和端口，跑完关掉。交付前运行 `make check`；改到数据库或队列时，再在真实 PostgreSQL/RQ 上跑一次提问到报告的完整流程。

## 设计决策

### 决策 0001 注释不引用评审轮次

注释说明今天的理由；只有带着历史才讲得清的理由（版本序列、争论过的取舍）记在本文，代码指过来。具体的失败案例写成失败本身，不写轮次号。存进数据的版本标识（生产者、`checker_version`）保持写入时的样子，读的时候原样显示。

### 决策 0002 测量的生产者与核验器版本（已被 0010 取代）

雷达自己最后写的是 measure.v9 + checker v16（之后 measure.v10 的规则原样搬进 Fabric）。旧行按写入时的版本读，`research/measure_history.py` 原样显示 `checker_version`，从不重核或改标。

### 决策 0003 完整可比域

同名指标常常不可比（报告日 vs 发病日、分母不同、同一记录里两个组）。只有指标族确定、且该族要求的每个维度都被证实（逐维核验或由核验器匹配的字段承载）时才自动比较；unknown 从不当「不适用」。有缺口的点照常存、作为线索列出缺口，不参与比较。组键用定长哈希拼族和维度；同一记录同一组两个不同值都保留、都不比较；升级后的点接替旧点（`hand_over`）。代码：`research/domain.py`、`series_sync._join`。

### 决策 0004 上一轮报告与已撤权来源

追问带着上一轮报告规划，而那份报告的来源可能后来被撤权。规则：只有它整条链上的每个来源现在都可读时才用，每次使用和每次对外调用前都查，查不过就以 `upstream_access_withdrawn` 停下；链条成环、断开或超过 `LINEAGE_DEPTH` 算未知，不算「没有更早来源」。对外视图里，继承了不可读报告那一轮模型写的东西整体隐藏，只留程序文字、自身记录仍可读的短引、只由用户原话组成的检索词和停止原因。存储不改，视图按请求时 Fabric 的来源清单现算。代码：`research/pipeline.py`、`app.py`（`redact`）。

### 决策 0005 发布标记与来源撤权

- 报告 BioCheck 状态是 PASS 且各节齐全才 `publishable: true`；其余 `publishable: false`、`hold: pending_verification`，`hold_reason` 写原因（`biocheck_timeout`、`not_checked`、`biocheck_<status>` 等）。planner 和模型从不设这几个字段，也不得为放行改成 PASS。标记不藏东西：待核报告的草稿、评估和逐句意见照常显示。
- 来源以 Fabric `/api/fabric/sources` 为准（成功缓存 5 分钟，失败不缓存）。所有出口（原文、详情、列表、导出、专题、观测）输出时统一检查；引用了当前不可读来源的分析，相关正文隐藏。每次带证据的外发（模型、BioCheck、MechEvidence）前都向 Fabric 确认来源仍可读。
- 监测的出口同样先给程序事实，再给模型判断。代码：`research/views.py`、`research/run/submit.py`、`research/topics.py`。

### 决策 0006 待核的上一轮报告只作为待核线索

`analyses.create` 记下父分析的 `report_status` 和发布标记；`lineage.previous_check` 给出 `{report_status, pending}`（没有状态的旧记录算未核）。规划和 BioCheck 都收到这个标记，待核报告的草稿前面加固定标签，只能提供对象、检索方向和待核线索，不能写成已确立，也不绕过新一轮的发布标记。

### 决策 0007 RQ 负责送达，数据库租约负责归属

- RQ 只把分析 id 送到 worker；丢任务、重启 Redis、重复入队都不能丢或重复结果，权威状态不在 Redis。
- 数据库租约管归属、幂等、隔离和恢复：`SELECT … FOR UPDATE SKIP LOCKED` 认领，写令牌和到期时间；只有持有未过期租约的才能提交，过期的工人不能覆盖接手者；失败计一次尝试、退避，到上限转终态留待复核。
- 分析的租约也带令牌（`analyses.lease_token`）：每次写入（进度、证据、外发记录、模型调用、结果）和每次对外请求前都在行锁里核对「令牌仍是自己的且未过期」并续租；被取代的 worker 得到 `lease.Lost`，什么也不写。失去租约前已发出的请求，晚到的回答仍记入旧尝试的审计并计入预算。
- monitor 每轮调 `analyses.recover`，把租约过期或没进 Redis 的分析重新入队；外发记录停在 `prepared` 的，原样保留、在 notes 记 `recovered_unknown_outcome`，不猜。
- 这些保证只能在真实 PostgreSQL 上验证（`make test-pg`）。

### 决策 0009 来源能力由 Fabric 声明；MechEvidence v2

- `GET /api/fabric/sources` 每个来源带 `capabilities`，`adapters/capabilities.SourceCapabilities` 要么整份读要么不读；雷达不再保存任何来源集合（`tests/test_no_source_sets.py` 防回潮）。能力未知时不抓新、不读附件、不做登记比对，记一条 note，不用内置兜底。只有 `capabilities.select` 为真的来源可被新分析选中（否则 422 `source_not_selectable`）或监测。
- `BIORADAR_MECHEVIDENCE_CONTRACT=v2`：规则只在 MechEvidence 一处。雷达组请求，向 `POST /v2/reuse-key` 要评价器、reuse key 和材料回显（查缓存、判断单份材料能否发送都靠它）；发出前向 Fabric 重读材料；为每次评价签发授权（`model_attempt_authorizations`），在 `/internal/v1/model-attempts/*` 回答服务的每次模型请求；收到回执后按 `GET /v2/contract` 发布的 JSON Schema 校验形状、与 reuse-key 答复逐项比对，并核对自己的尝试账本（`mech/ledger`），全部一致才采用。契约取不到或不是 v2 时不发送（`mechevidence_contract_unavailable` / `_invalid`）。

### 决策 0010 测量归 Fabric，雷达只管专题的选择

- Fabric 负责一切客观测量：抽取、BioCheck 核验、覆盖与欠账、更正与撤回、处理器和核验器升级。雷达的分诊只做分类（专题、警报、信号、对象、关注、结案），不抽数。
- 雷达保留调查自己的选择：`series_points`（哪个专题把哪个 Fabric 对象放进哪条序列）、完整可比域门槛（决策 0003）、序列计算、序列/更正/记录内矛盾事件及其触发的分析。
- `series_sync` 是 `monitor.tick` 的一步，不调模型：变更流 `GET /api/fabric/measurements/changes` 一页一页存进 `measurement_inbox`，页和游标同一事务提交；分诊把版本放进专题时按版本拉 `GET /api/fabric/measurements`；两种先后顺序结果相同、各连一次（唯一约束 + 保存点）。来源撤权期间扣下的事件恢复后按版本重拉。分析运行时每个点的状态按截止时间、以当下权限重新读。
- 雷达原来的八张测量表连数据保留，冻结为只读（迁移 0023 的触发器拒绝写入和清空，会话层也拒绝）；旧点照常显示为 `authority: radar_history`，从不算当前。

### 决策 0011 报告分节和五项检查

完成的分析存 `result.sections`，由程序从运行状态拼出、不调模型：`question`、`judgment`（主要判断、业务影响）、`evidence`（支持和反对）、`gaps`（局限）、`scenarios`（会改变判断的证据）、`visibility`（截止、读了什么、关键缺口；附录里每条记录分列 `published_at`、`first_seen_at`、`proof_available_at`、`replay_mode`，没有的写「未知」）、`recommendation`（目前为空，原因 `no_objectives`）。填不了的节标 `missing` 和原因；有缺节的报告即使 PASS 也标待核。代码：`research/run/sections.py`。

### 决策 0012 候选组和命题编号

没有成员表。专题分析在 `result.groups` 里存它最新材料所在的组（展示组），按截止时间算：成员只按明确依据连接（`same_record`、`fabric_relation`、`event_id`、`text_reference`），每个成员带依据、经由谁连接和 `confirmed_at`；候选是只靠键（病原+地区 30 天内、或地点+定位句）靠近的别组材料，单列、不计数、不移动起止时间。`backfill_run_ids` 指定的回填版本只作背景，不进计数、基线和首次可见时间。判断的命题编号（`prop_id`、`question_key`、`content_rev`）在存结果时分配，专题内单调（迁移 0024）。代码：`research/groups.py`、`research/propositions.py`。

### 决策 0013 来源与通道分开；每次 planner 调用可重建

- 候选和历史项带真实 `source`，检索另带 `channel`（`fabric_literal` / `weknora_semantic`）；阅读没有通道。语义检索每个来源提供一次、召回限在该来源。每轮声明全部四个通道：图谱 `03_not_run`、GDELT 线索 `not_supported`、语义检索关闭时 `not_configured`。
- 每次 planner 调用在 `progress.decisions` 追加一条：不含历史的请求、`history_ref`（动作数和哈希）、整份请求的 `request_sha256`、完整响应、planner 的 `/health`、`action_index`；失败和停止也记。历史由 `actions[:n]` 重建，哈希对得上才算同一请求。一次分析合计不超过 1 MiB，放不下的那一轮只留哈希并标 `snapshot_truncated`。
- planner 的 `/health` 没有 `channels` 时以 `planner_outdated` 停下。代码：`research/run/decisions.py`、`research/run/investigate.py`。

### 决策 0014 按断言单元核验，报告按槽写

- 核验走 `POST /v2/verify`（`BIORADAR_BIOCHECK_VERIFY=v2`，`v1` 是退路）。每个请求带 `sections: [{kind, start, end}]`，即草稿每段的位置和节类型；评估结论作为一个 `judgment` 节核验，分句由 BioCheck 做。回执放在 `report.claims`，每个版本记 `checker_version` 和 `rules_version`。
- 写稿前程序把规划的判断问题列成槽 J1、J2…，写稿和评估都按槽引用；槽的命题编号在存结果时才分配（决策 0012），写稿时不告诉模型。目前每个槽都是 `free` 问题。
- 某一槽段落写成立、评估判不足时，用剩下的修订额度改写并重核，仍不一致则待核。代码：`research/run/slots.py`、`research/run/report.py`、`research/run/assess.py`。

### 决策 0015 命题所依据记录的新版本

监测轮不调模型地查看每个触及专题的新版本（旧版本放进过专题或被专题分析读过，或它更正/撤回这样的记录），按读取时的模式和截止时间问 Fabric 的 `/api/fabric/version-differences`，写一条 `version` 事件：原因、Fabric 的差异种类、`reason`、`sample`，以及 `affected`（依据旧版本的命题）。更正/撤回 → `source_corrected`，优先重判；`raw_changed`、`serialization_only` → `pending_review`；只是投影、正文或字段位置变动 → `processing_upgrade`；这些命题都要重判。每个版本和原因只写一次。代码：`research/revision.py`、`research/scheduling.py`。

### 决策 0016 新闻索引线索

新闻索引的记录（`LEAD_SOURCES`：GDELT）是线索，不是其来源的陈述。监测照常分诊，但只保留相关性（`observations.relevance`：related / unrelated / uncertain）；线索不进专题、不触发警报、永远未核。在候选组里，只有线索的组确认成员数为 0、没有起止时间，排在有确认成员的组之后；线索通过明确依据连到别的来源材料时才随那个组计数。读取时线索单独取最新的 `MAX_LEADS` 条，不挤掉新闻。代码：`adapters/fabric.py`、`research/triage.py`、`research/groups.py`。
