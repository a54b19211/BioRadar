## 三个人先一起跑一遍

在“提问与调查”输入：

> Elranatamab 治疗复发/难治性多发性骨髓瘤，作用机制和疗效的现有证据分别到哪一步？哪些资料仍不足以支持布局决策？

看它如何查询、取得材料、评价机制、编写和检查报告，再追问：“能否证明一线治疗中优于现有方案？”核对研究人群、对照和结果是否已经公布。追问另存一版，原报告保留。

可重复运行的例子是 `scripts/research_e2e.py`，方法见[开发说明](开发说明.md)。它调用真实来源和模型，不预填答案；验收行为和依据，不要求每次措辞相同。后台发现线索和长期专题更新也进入这套调查，不另做一套“主动模式”。

## 李明洋：路由方法与可靠接入分别交付

**第一项：接手完整研究流程。** 从 `analysis_service.py` 的创建、初始查找、补查、模型调用和最终报告开始读。自己画清每一步的输入、输出和保存位置。准备正常研究、来源失败、额度不足各一个例子，交给另外两人从页面核对。

完成标准：只输入问题即可开始；重复提交不创建第二份任务；每次模型请求都有阶段与用量；查询单独计数；用户预算只能低于服务上限；中断后按原记录接续。用量缺失要说明估算方式，结果不明的已发请求保留状态，避免重复付费。额度用完后仍能看已经取得的材料和停止原因。

**第二项：把 WeKnora 接到真实原件。** 配置现有服务、知识库和服务端凭据。先核对返回项的原记录身份，再读取 Data-Fabric 的固定版本。只有标题相似的结果仍是候选，不能替代原件。

完成标准：实际检索至少取得一份可读回的同一原件；重复、原件不存在和来源撤权分别有正确结果。检索平台继续在 WeKnora 维护。

**第三项：扩大连续运行。** 先测任务等待时间、单次研究用时和实际用量，再调每小时额度。增加来源前确认正文、身份、时间和更新规则能进入既有结构。

完成标准：一批新资料进来后，能解释哪些进入调查、哪些合并、哪些等待；重启保留处理位置和旧报告。徐的采集、唐的图方法各由本人维护，雷达接入问题由李明洋承担。

## 孙博文：让研究真的有增量

**第一项：提高补查效果。** 把问题拆成能验证的缺口。比如“是否优于标准治疗”需要同人群的对照结果；“为什么终止”需要具体原因。优先查会改变结论的缺口，记录没有找到的查询和已经覆盖的范围。

完成标准：补查取得的新材料明确支持、反对或收窄了一个判断；没有新材料时解释停止原因。用同一问题比较一次检索与继续补查，研究数量按独立研究统计。

**第二项：使用汪、潘的结果。** 汪指出机制链哪一步弱，雷达安排查什么；潘指出哪句话没依据，雷达区分缺资料还是表达错误。缺资料继续查，表达错误交由潘的方法修订。

完成标准：一项真实反证能改变判断；单纯改写措辞不算新增证据。页面能对应“新材料—受影响判断—修改理由”。机制打分和文字核验不要在雷达再实现一份。

**第三项：按方向做好分析数据和发现方法。** 四方向并行明确统计单位、真实来源和评价标准，再分批实现适用算法。已有方法在 `research/mining/registry.py`，按输入条件扩展：

| 方向 | 输入 | 应给出的线索 |
|---|---|---|
| 管线竞争 | 登记、规范项目身份、阶段与状态历史 | 谁进入、退出、推进，统计口径是什么 |
| 新研究组合 | 去重论文、技术/靶点/疾病、发表时间 | 哪个组合开始出现，过去基数和独立研究数是多少 |
| 机制与成熟度 | 汪的评价、原文及时间 | 哪一步获得新支持，哪些反例仍存在 |
| 安全与监管 | 正式通告、撤回、更正、项目关系 | 哪项现有判断需要优先复查 |
| 商业、公共卫生、区域 | 对象、数值、单位、期间与范围 | 可比较的变化，排除补录和口径变化 |

完成标准：每种方法有真实正例、误报例和不足以计算的例子；解释为什么值得调查。缺字段给徐或唐具体记录和用途，算法效果与误报处理由孙博文负责。

**第四项：做历史评价。** 先固定当时可用资料与当时判断，再接后来的结果。选一个小而完整的范围，包含成功、失败和没有后续结果的对象。

完成标准：执行时读不到未来资料；同一批资料可比较新旧方法；分别记录误报、漏报、提前量和覆盖范围。今天倒查的历史只能算重建，不能称为当时发出的预警。

## 刘金彦：页面和评价都要写代码

**第一项：让外人自己用。** 维护提问、调查进度、证据、报告、追问和旧版切换。显示实际步骤与用量；错误提示写清下一步操作；后台刷新不能清空正在输入的追问。

完成标准：找未参与开发的人，从提问到下载独立完成，把卡住的地方修掉。

**第二项：做好报告与依据。** 页面、Markdown 和 JSON 对应同一保存版本。最终核验针对哪份文字就标在哪份文字上；前期分析另列。支持、反对材料都能找到，引用可以读回原文。

完成标准：下载后逐字对照正文；追问后原报告和引文仍可读；原文暂不可读显示原因，不换成另一篇材料。

**第三项：建立独立评价集。** 每个用例保存问题、截止时间、可用资料、关键事实、重要反例和常见错误。第一组覆盖：人群混用、预计日期当实际结果、登记状态当终止原因、重复论文算独立支持、图谱关系当因果证据、重要反证遗漏。

完成标准：普通模型、现有问答与雷达使用同一问题和资料比较。错误定位到具体句子和原文，再评价是否帮助决策，不只给综合分。 本轮已有可复用例子：把报销建议写成已经报销、把治疗开始后的观察期写成治疗前、引用选到同一原文的错误片段。具体版本和实际核验结果保存在 `evaluation/handoff-verification.json`，从这些例子开始维护评价集。

- 李明洋维护固定原件绑定、统一模型调用和故障恢复。继续扩接新来源时，要检查超时、重复投递、结果保存失败；复用现有调用记录，不能靠重新发请求解决恢复问题。WeKnora 旧资料缺编号时的兼容限于已选原件，后续完善元数据由来源端完成。

- 刘金彦维护报告阅读和独立验收。分别展示全文核验与所选片段复核，检查用户看到的全文与数据库、导出是否相同。用已有正确、错误和待核案例检查变化，保留失败样例，不把测试目标设成每份报告都显示通过。

## 逐步查询交接后的工作

李明洋维护 `analysis_service.py`、接入适配器、权限、保存与恢复；query-planner 的独立方法和训练实验由他所在课题维护。先跑一次首问和追问，核对每项查询的回执、采用原件和实际费用。worker 重启先查回执，已有结果不能再付费发送。交付是可恢复的真实执行与接口。

孙博文维护 `query_policy.py`、`analysis.py` 和现有挖掘方法，负责研究问题、候选构造和证据缺口如何影响下一步。他要给出支持、反证、竞争、类似失败、技术、专利的具体口径，抽查未选资料，说明误报和漏报。模型说“资料够了”必须能指出原件依据。不要复制李的工具执行、潘的正文核验或唐的图谱算法。

刘金彦维护过程与报告页面、导出和评测脚本，让用户看清已取得什么、哪些请求失败或没做、哪些问题仍缺证据。用同一组问题比较 baseline 与 query_planner，保存首问、追问、自动发现、后到证据和历史时点的实际结果。文字核验与调查完整度分开计分；旧资料补录的误报也记入结果。

三人共用 `evaluation/handoff-verification.json`。各改自己的模块，用实际输入和回执对齐；李负责合入部署，不代写另外两人的研究与页面代码。

接手时先看这次留下的真实失败：首问还存在概括过宽和核验问题；追问纠正了范围，但核验回执没有通过引用和范围约定。李检查调用与恢复，孙逐条查证研究结论和缺失资料，刘检查页面是否把待核原因讲清楚，再用同一批记录评价改动。不要为了让状态变绿反复生成。

## 开发顺序

先按开发说明核清原件、索引、图谱、分析数据集与服务边界。李明洋负责来源到 KB/版本绑定及路由契约，孙博文负责四方向的单位、数据加工和算法资格，刘金彦在方法调优前建立独立验收集并抽查未入选材料。各方向先完成至少一种真实可用的 KDD 链，再扩大方法、来源与持续时间；任何一个例子通过都不替其他方向背书。涉及 Fabric 的修改须先按用户要求拉新分支。

沿现有主线做普通 Git 提交。不要每改一版就开分支，也不要在别人有未提交工作时强行重置目录。
